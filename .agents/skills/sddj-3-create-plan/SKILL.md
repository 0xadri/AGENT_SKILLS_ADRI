## Source of Truth: Two Distinct Authorities

This skill operates with two different sources of truth that answer two different questions:

**"What to build?" → the reviewed input spec is authoritative.**
The spec at `docs/plans/[feature-name]_spec.md` must have `status_doc: reviewed` before this skill proceeds (enforced in Step 2). A reviewed spec is the canonical requirements document. Trust it for what needs to be implemented.

**"What already exists?" → the codebase is authoritative.**
The code reflects the real current state of the system. Specs, plans, and docs drift over time — the repo does not lie.

**Consequences:**

- If the spec says "add field X" but field X already exists in the code → **flag to the user** before writing the plan. The spec has an error that needs correction.
- If the plan's steps conflict with what's actually in the codebase → **silently update the plan** to match the code. No confirmation needed — the plan is just a document.
- `docs/plans/*` other than the input spec → draft specs, secondary to the code. Verify any concrete claims against the actual codebase before using them.
- `docs/plans_done/*` → archived/completed plans, frozen after implementation. Useful for historical context and rationale (e.g. why a pattern was chosen), but any specific claim (file paths, function names, data shapes) must be verified against the current code before being trusted.

## Guidelines

- The plan is a step-by-step implementation guide derived from a spec document.
- TDD is an implementation mode within this same workflow, not a separate document type.
- Plan ordering must match implementation order — each step should be buildable on top of the previous one.
- When the feature spans multiple packages, always order: **backend first → shared package → frontend**. This ensures API contracts and shared types exist before the frontend consumes them.
- Each step must reference concrete file paths and describe the exact changes needed.
- Include validation criteria for each step so the implementer knows when the step is complete.
- When the plan uses TDD mode, steps must be written as behavior slices that can be executed in **RED → GREEN → REFACTOR** order.
- In TDD mode, each step's `Validation` block is the step-level gate; the plan's `## CFL Verification` section is the final full-feature gate and must not duplicate per-step checks.
- Include a "Decisions Made" section to document any choices or assumptions.
- Include a "File Index" table summarizing all files touched and what changes.
- Match the format and conventions of existing plans in `./docs/plans/`.

### Canonical Section List

Use this as the authoritative reference for which sections to include and when.

**Always include:**

| Section                                              | Notes                                                                                                  |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| YAML frontmatter                                     | See template below                                                                                     |
| `implementation_mode` in frontmatter                 | `direct` or `tdd`                                                                                      |
| `> Xmin read, for Y words and Z lines`               | Estimated read time — filled in by `/sddj-read-time`                                                    |
| `# [Feature Name] — Implementation Plan`             | H1 title                                                                                               |
| `## Table of Contents`                               | Generated by `/sddj-table-of-contents`                                                                  |
| `## IMPLEMENTATION STATUS: READY FOR IMPLEMENTATION` | Phase-by-phase status table with ⏳ Pending                                                            |
| `## Overview`                                        | 1–3 sentences describing what this plan implements, referencing the spec                               |
| `## Decisions Made`                                  | Table of key decisions and trade-offs — document non-obvious choices                                   |
| `## Phase N — [Backend / Shared Package / Frontend]` | One phase per package area; use `### N.N · Step Title` sub-steps                                       |
| `## Implementation Checklist Summary`                | Grouped checkbox list (Backend / Shared / Frontend / Testing)                                          |
| `## CFL Verification`                                | Final full-plan gate only: checked off by `sddj-6-implement-plan` once the plan reaches completed state |
| `## Review History`                                  | Appended by `sddj-7-review-implementation` after each review run                                        |
| `## File Index`                                      | Table of every file touched and the nature of the change                                               |

**Include when applicable:**

| Section                    | When to include                                                                                      |
| -------------------------- | ---------------------------------------------------------------------------------------------------- |
| `## Implementation Order`  | When the dependency chain between phases is non-obvious and worth calling out explicitly             |
| `## Dependencies`          | When the feature relies on specific external libs, services, or other features that must exist first |
| `## Success Criteria`      | When there are clear, measurable outcomes to validate the feature is complete                        |
| `## Future Enhancements`   | When scope is intentionally deferred — "yes, but later" items                                        |
| `## Related Documentation` | Links to the spec, other plans, ADRs, Swagger, or external docs                                      |
| `## Notes`                 | Miscellaneous implementation notes that don't fit elsewhere                                          |

**Avoid unless truly needed:**

| Section                | Why to avoid                                   |
| ---------------------- | ---------------------------------------------- |
| `## Risk Assessment`   | Only for high-risk features with many unknowns |
| `## Executive Summary` | Only for very large plans (10+ phases)         |

## Steps

Execute the steps below sequentially.

### Step 1 — Resolve the feature name and spec path

**Case A — `$ARGUMENTS` looks like a file path** (contains `/` or ends with `.md`):

- Use it directly as `[spec-path]`.
- Extract the feature name from the filename: strip the directory prefix and the `_spec.md` suffix (e.g. `docs/plans/user_trips_spec.md` → `user_trips`). If the filename doesn't follow the `_spec.md` convention, use the full basename without extension as the feature name.
- Normalize the feature name: replace hyphens with underscores.

**Case B — `$ARGUMENTS` is a plain name** (no `/`, doesn't end with `.md`):

- Normalize it: replace hyphens with underscores (e.g. `user-trips` → `user_trips`).
- Set `[spec-path]` to `./docs/plans/[feature-name]_spec.md`.

**Case C — `$ARGUMENTS` is empty**:

- List available spec files using the Glob tool with pattern `docs/plans/*_spec.md`, then strip the directory prefix and `_spec.md` suffix from each result to show the feature names.

- Ask the user which spec to create a plan for, then apply Case B logic.

From this point forward, `[feature-name]` and `[spec-path]` are fully resolved and used consistently throughout all remaining steps.

### Step 2 — Read the spec and resolve open questions

Read `[spec-path]` (resolved in Step 1).

If the file does not exist, inform the user and stop.

Check the spec's frontmatter for `status_doc`. If its value is `"draft"` (or missing entirely), warn the user: "This spec is still in draft and may not be finalized. Building a plan from it now could result in rework if requirements change. Proceed anyway?" Stop if the user says no.

If the spec has an `## Open Questions` section with unresolved items:

- Present each open question to the user and ask for an answer before proceeding
- For each answer received: update the spec (move the item from Open Questions to Key Decisions, or annotate inline) and record it in the plan's `## Decisions Made` table
- For each question the user cannot or does not answer: document the assumption being made, record it in `## Decisions Made` as `"Assumption (unanswered: [question])"`, and flag it inline in the relevant plan step
- Do not proceed silently — every open question must result in either a confirmed answer or a documented assumption

### Step 3 — Calibrate depth

Based on the spec's complexity (size of Technical Design, number of phases, scope of changes), estimate the recommended plan size:

- **Minimal** (~1–2 steps total, 1 phase, ~1 question, 2–5 min) — trivial change, single file or config tweak, no optional sections
- **Compact** (~3–5 steps total, 1–2 phases, ~3 questions, 5–10 min) — small feature, single package, minimal optional sections
- **Standard** (~8–15 steps, 2–3 phases, ~5 questions, 10–20 min) — typical multi-layer feature; all mandatory sections, select optional ones
- **Detailed** (~15–25 steps, 3–5 phases, ~7 questions, 20–35 min) — complex feature touching many layers; most optional sections included
- **Exhaustive** (~25+ steps, 4+ phases, ~10 questions, 35–55 min) — large-scope or high-risk feature; all sections, full testing strategy

Use `AskUserQuestion` with two questions:

1. **Preferred plan depth** — offer the 5 options above, marking your recommendation (e.g. "Standard (Recommended)"). Adjust option labels to reflect your estimate (e.g. "Standard (~12 steps)").
2. **Optional sections** — which optional sections should the plan include? Make it explicit that selected options will be included and any unselected options will be skipped. Available: Implementation Order, Dependencies, Success Criteria, Future Enhancements, Related Documentation, Notes, Risk Assessment, Executive Summary.

Then ask one more question:

3. **Implementation mode** — `Direct` or `TDD`.
   - `Direct` → standard implementation steps with validation.
   - `TDD` → every implementation step must define the failing test first, the minimum code to make it pass, and any allowed refactor scope.

Adjust step granularity and section list for the rest of the plan accordingly.

### Step 4 — Explore the codebase for context

Using the spec as a map — primarily its **Technical Design** section (Data Model, API/Backend Changes, Frontend Components) — explore the codebase systematically. If the spec has no `## Technical Design` section or uses different section names, use the full spec as input and note upfront that the exploration will be less targeted than usual.

1. **Find the files** — For each file path, endpoint, type, or component mentioned in the spec's Data Model, API/Backend Changes, and Frontend Components sections (or equivalent), read it to understand its current state and exact structure.
2. **Check for partial implementation** — Search for identifiers from the spec (function names, type names, route paths, component names) that already exist in the codebase. Any area already implemented must be marked as done in the plan, not re-planned. If something the spec plans to add already fully exists in the code, flag it to the user — the spec may need correction.
3. **Learn the patterns** — For each package area the plan will touch, read 1–2 similar existing implementations to understand naming conventions, file structure, and abstractions in use. The plan must follow existing patterns, not invent new ones.
4. **Map dependencies** — Note what the feature depends on: existing services, shared types, third-party libs. Flag anything that needs to be installed or isn't yet available.

**The codebase is the ground truth for current state.** If the spec describes something that doesn't match what's actually in the code, note the discrepancy. Findings from this step override spec claims about what currently exists.

This context is critical for writing accurate file paths and realistic implementation steps. Do not skip it.

### Step 5 — Approve structure and scope

Present a high-level outline for the user to approve **before writing the full plan**. At this stage, show structure only — no step-level detail yet:

- Proposed phases and which package each covers
- Step titles per phase (1 line each, no implementation detail)
- Chosen implementation mode (`Direct` or `TDD`)
- Scope decisions or trade-offs worth flagging upfront (e.g. what's in vs out, assumptions made)
- Which optional sections will be included (e.g. Success Criteria, Future Enhancements)

Ask: "Does this structure and scope look right? Anything to add, remove, or reorder?"

Do not write the full plan until the user approves the structure. Iterate on the outline if needed.

### Step 6 — Write the implementation plan

Before writing, use extended thinking to reason through: how all spec requirements map to concrete steps, the right phase ordering and dependencies between steps, potential implementation gaps or conflicts, and any tradeoffs worth capturing in Decisions Made.

Before writing, check if `./docs/plans/[feature-name]_plan.md` already exists. If it does, ask the user: "A plan for this feature already exists. What would you like to do?" with these options:

- **Overwrite** — discard the existing plan and write a new one from scratch
- **Create new version** — create `[feature-name]_plan_v2.md` (or `_v3`, etc., incrementing until unused), leaving the existing file untouched; notify the user of the new filename
- **Abort** — stop here

Do not proceed until the user responds.

Then create (or update) `./docs/plans/[feature-name]_plan.md` using the structure below. Omit optional sections if they don't apply.

Set `implementation_mode` in the plan frontmatter:

- `implementation_mode: "direct"` for normal execution
- `implementation_mode: "tdd"` when the user selected TDD mode

If `implementation_mode` is `tdd`, write every implementation step as a thin vertical slice of behavior. Do not group multiple unrelated behaviors into one step just because they touch the same layer.

After writing the plan, update `./docs/plans/[feature-name]_spec.md`: add the plan to the spec's `related_docs` frontmatter if it isn't already listed there:

```yaml
related_docs:
  - path: "docs/plans/[feature-name]_plan.md"
```

**Phase ordering rules:**

- Backend changes → always Phase 1
- Shared package changes → always before Frontend (Phase 2 if backend also changed, else Phase 1)
- Frontend changes → always last
- Single-package features → one phase, no need to number it
- Within a phase: foundational/schema changes first, then services, then controllers, then tests

**Step granularity rules:**

Each step must be one coherent, testable unit of work. Right-size steps by this guideline:

- Target 1–3 files per step
- A step should be completable and verifiable independently before moving to the next
- Too fine (one-field change per step): merge into a larger logical step
- Too coarse (entire feature layer as one step): split by sub-component or concern
- Tests for a step belong either at the end of that step or as a dedicated testing step at the end of the phase
- In `tdd` mode, prefer behavior-first vertical slices over layer-first slices whenever both are reasonable.

**Testing coverage is mandatory:**

Every phase must include at least one step (or explicit sub-tasks within a step) that covers testing and validation. Do not write a phase with only implementation steps. Acceptable forms:

- A dedicated `Step N.N · Tests` at the end of the phase
- A `**Validation:**` block within each step with concrete test cases
- Both (preferred for backend phases)

A plan that ships with no test steps is incomplete and must not be finalized.

For `tdd` mode specifically:

- Every implementation step must include `Test Level`, `RED`, `GREEN`, `REFACTOR`, and `Validation` blocks.
- `RED` must describe a failing test for the behavior in that step, not a test to be written later.
- `GREEN` must stay minimal; defer adjacent improvements to later steps or the step's `REFACTOR` block.
- Do not add a separate testing-only step for behavior that should already be covered by the step's own RED/GREEN/REFACTOR cycle.
- Use each step's `Validation` block for targeted step-local checks only. Reserve `## CFL Verification` for the end of the full plan.
- Do not require a full `Build` after every TDD step unless the specific step's validation truly needs it. Keep `Build` in the final CFL gate by default.

**`related_code` frontmatter:**

Leave `related_code` as a placeholder (`[]`) when first writing the frontmatter. After the File Index is complete, go back and populate `related_code` with the most important file paths from the index (primary files touched, not every file).

**Granularity self-review (before presenting to user):**

After writing all phases, do a single pass over all steps and ask: are they consistently sized? Check for:

- Any step that covers 5+ files (likely too coarse — split it)
- Any 3+ consecutive steps that each touch only 1 small thing (likely too fine — merge them)
- Steps in early phases with 10+ bullet points under Changes vs steps in later phases with 2 vague lines (granularity drift — expand the vague ones)

Fix any issues found before moving to Step 7.

### Step 7 — Triple-check consistency

Use Grep and Read to verify the plan is fully aligned with:

- The spec (`./docs/plans/[feature-name]_spec.md`) — every requirement in the spec must be covered by a step in the plan
- The current codebase — if parts of the feature are already implemented, the plan must reflect that (mark as done, skip, or adjust)

Identify any inconsistencies:

- Steps in the plan that contradict what the spec says
- Spec requirements missing from the plan
- File paths, function names, or types that don't match what's actually in the codebase
- Stale assumptions (e.g., a pattern the plan references that no longer exists)
- In `tdd` mode, any step missing `RED`, `GREEN`, `REFACTOR`, or `Validation` blocks

**Resolving conflicts — two different rules depending on what conflicts:**

- **Plan vs codebase** — the code wins. Silently update the plan to match the actual code. No confirmation needed.
- **Spec vs codebase** (spec describes something that conflicts with reality) — flag to the user. The spec may need correction before the plan can be finalized. Do not silently paper over spec errors.

### Step 8 — Approve the detail

Present the completed plan to the user for final approval. Focus this review on **detail and correctness**, not structure (that was approved in Step 4):

- Are the individual steps accurate and complete?
- Are the file paths and function names correct?
- Are the Decisions Made entries correct?
- Is anything missing, over-engineered, or unclear?

Ask: "Does the plan look correct and complete? Any steps to adjust before I finalize?"

Iterate on specific steps if the user has changes. Do not rewrite the full plan unless the structure fundamentally changed.

After any step changes, immediately sync these two sections to reflect the updated steps before finalizing:

- **Implementation Checklist Summary** — add/remove/rename checklist entries to match
- **File Index** — add/remove rows for any files added or dropped

### Step 9 — Check for unfilled placeholders

Before finalizing, scan `./docs/plans/[feature-name]_plan.md` for any remaining placeholder text that was not filled in:

Use the Grep tool to search for `\[.*\]` in `./docs/plans/[feature-name]_plan.md`. Exclude lines matching `^\s*-\s*\[` (markdown checkboxes) and lines starting with `<!--` (HTML comments).

If any matches are found (excluding markdown checkboxes `- [ ]` and HTML comments), list them and fill them in before proceeding. Do not finalize a plan with unfilled placeholders.

### Step 10 — Finalize doc metadata

Run these skills sequentially on the plan file:

1. `/sddj-frontmatter` — set `status_doc` to `"draft"` (do not ask the user)
2. `/sddj-imp-status` — set status to `"PENDING: spec must be reviewed before implementation can start"` (do not ask the user)
3. `/sddj-table-of-contents`
4. `/sddj-read-time`
